Identificar una placa boliviana en video/fotogramas capturados por un teléfono Android.

4.2 Flujo de un vehículo
El operador inicia sesión con Google en la app Android y selecciona la caseta y el sentido de circulación (ENTRADA o SALIDA).
En Modo Caseta, el teléfono muestra la cámara y captura un fotograma cada 500 ms aproximadamente (2 FPS). No se envía cada frame a máxima resolución: redimensionar y comprimir JPEG de forma razonable.
La app envía el frame por HTTPS a POST /api/v1/pasos/frame en el VPS con caseta, sentido, token y un identificador de sesión.
FastAPI valida el token, registra una detección y reenvía el frame al endpoint único de RunPod con INFERENCE_API_KEY.
RunPod ejecuta M1 + OCR, M2 y M3; devuelve placa, confianza, categoría, ejes, keypoints y latencia.
FastAPI aplica deduplicación, consulta tarifa/vehículo/saldo, calcula el monto y decide el estado. Si no hay confianza suficiente, marca REVISIÓN_MANUAL y no realiza cobro automático.
FastAPI guarda paso/evidencia/alerta y, si procede, descuenta saldo dentro de una transacción atómica.
FastAPI emite evento SSE. El panel web muestra paso, imagen, datos, importe, estado y hora sin recargar.
La app móvil recibe el resultado y lo muestra al operador.
REGLA CRÍTICA DE DUPLICADOS
Como la app envía 2 frames por segundo, no se debe guardar cada frame como un paso distinto. Implementar deduplicación por placa + caseta + sentido con una ventana configurable inicial de 45 segundos. Si la placa no se lee, usar hash de imagen/sesión y una ventana corta. Nunca bloquear un paso real solo por duplicación sin dejar registro de la detección.

4.3 Actualización en tiempo real
Usar SSE (Server-Sent Events) en GET /api/v1/events/stream. Emitir eventos step.created, alert.created, step.updated y revenue.updated. El navegador se conecta desde el mismo dominio y usa una cookie de sesión HttpOnly para que EventSource no necesite un header Authorization personalizado. Enviar heartbeat cada 20 segundos y permitir reconexión. Caddy debe desactivar buffering para la ruta SSE.
5. Modelos de visión por computadora
NO CONFUNDIR LAS TRES TAREAS
M1 identifica la placa y lee sus caracteres. M2 clasifica el vehículo y genera máscara de instancia. M3 identifica centros de ruedas visibles mediante keypoints y estima ejes. No sustituir M3 por una regla basada únicamente en el tamaño del vehículo.

5.1 M1 — Detección de placa boliviana + OCR
Primero buscar en el repositorio los pesos, notebook, dataset y configuración del detector de placas ya trabajado en clases. Reutilizar el archivo de pesos que funcione; no reemplazarlo por un modelo aleatorio.
El detector localiza la placa y devuelve una caja delimitadora. Recortar la placa con margen y corregir perspectiva si el recorte lo permite.
Aplicar EasyOCR al recorte. Probar rotación/contraste solo cuando sea necesario; no modificar el texto sin dejar trazabilidad.
Normalizar: mayúsculas y eliminar espacios/guiones. Validar de forma inicial 3 o 4 dígitos seguidos de 3 letras (formatos ordinarios de placa PTA). El recuadro departamental separado no forma parte de la matrícula principal.
Guardar texto original, placa normalizada, confianza OCR, caja de placa y, cuando sea posible, imagen de evidencia.
Cuando la confianza sea baja, marcar REVISION_MANUAL y permitir que el operador corrija el texto antes de cobrar.
Validación de caracteres ambiguos: implementar sugerencias ponderadas O↔0, I↔1, B↔8, S↔5 y 3↔8, tal como se comentó en clase. La sustitución debe respetar la posición numérica/alfabética. No transformar silenciosamente una placa: sugerir coincidencias y pedir confirmación.
5.2 M2 — Segmentación de instancias y clase
Arquitectura: YOLO11n-seg (Ultralytics), transferencia desde pesos preentrenados y ajuste fino con dataset propio etiquetado en Roboflow.
Clases obligatorias: moto, auto, minibús, camión y bus. Mantener exactamente los mismos nombres/índices en Roboflow, data.yaml, modelo, backend y frontend.
Cada vehículo debe disponer de su propia máscara y confianza de clase. La categoría sirve para seleccionar la tarifa, no para adivinar ejes.
Dataset: incluir fotos propias añadidas por el estudiante y, si es necesario, material de Roboflow Universe como complemento. Registrar fuente, cantidad propia, cantidad externa, partición train/valid/test y aumentaciones.
Inspeccionar visualmente las anotaciones y corregir máscaras mal cerradas, etiquetas cruzadas y fuga de imágenes entre train/val/test.
5.3 M3 — Keypoints de ruedas para estimar ejes
Arquitectura: YOLO11n-pose personalizado, inicializado con pesos preentrenados y ajustado con keypoints propios.
La cámara para el conteo debe captar el vehículo de perfil/lateral. Se marca un punto en el centro de cada rueda visible del lado observado; en esa vista, una rueda visible representa el eje correspondiente.
Un objeto vehículo tendrá hasta 8 posiciones de keypoint ordenadas de adelante hacia atrás. Declarar kpt_shape [8, 3]. Los puntos inexistentes/no etiquetados se marcan como no visibles según el formato YOLO Pose. Mantener el mismo orden para todas las imágenes.
Contar únicamente keypoints predichos con confianza superior al umbral validado. No contar dos veces el mismo eje por ruedas de ambos lados. El conteo inicial mínimo permitido es 2 ejes.
Si un camión está parcialmente oculto o no hay perfil suficiente, no inventar el número: devolver ejes=null y marcar REVISIÓN_MANUAL.
El número de keypoints debe evaluarse frente al número real de ejes anotados. Reportar exactitud de conteo y MAE (error absoluto medio).
LIMITACIÓN FÍSICA IMPORTANTE
Un video frontal, muy oblicuo, nocturno o con ruedas tapadas no permite contar ejes con fiabilidad. El video de prueba debe incluir vehículos de perfil, buena luz, cámara estable y ruedas visibles. Si el docente usa otro ángulo, mostrar el caso como limitación/ revisión manual, no como resultado garantizado.

5.4 Un único endpoint de inferencia en RunPod
RunPod debe ejecutar un servicio FastAPI que cargue una sola vez los tres modelos al iniciar. No crear tres servicios separados ni cargar pesos en cada petición. El endpoint público es el proxy HTTPS de RunPod y la web API lo consume de forma privada mediante una clave de aplicación.
POST /predict
Header: X-Inference-Key: ${INFERENCE_API_KEY}
Body: multipart/form-data, file=<frame.jpg>
 
Respuesta JSON esperada:
{
 "plate":"1234ABC", "plate_raw":"1234 ABC",
 "ocr_confidence":0.94, "plate_bbox":[x1,y1,x2,y2],
 "vehicle_category":"camion", "category_confidence":0.91,
 "axles":3, "axle_keypoints":[{"x":0.2,"y":0.7,"confidence":0.88}],

Crear GET /health que devuelva estado de carga de cada modelo, VRAM disponible, versiones y uptime. Si falta algún peso, informar model_ready=false y nombre del modelo faltante.
El servicio debe escuchar en 0.0.0.0:8000. Exponer el puerto HTTP 8000 en la configuración del Pod. El proxy de RunPod será HTTPS y la aplicación debe validar una clave en cada request.
No dejar el endpoint de inferencia sin protección: el proxy de RunPod es público. No confiar en que la URL del Pod sea un secreto.
Mantener cada inferencia acotada a una imagen y responder con rapidez; si una tarea excede el timeout del proxy, reducir tamaño/tiempo de procesamiento y evitar operaciones largas sincrónicas.

6. Reglas del peaje y base de datos
6.1 Reglas de cálculo y registro
El monto se obtiene de tarifas[categoria, ejes]. La aplicación no debe inventar un monto cuando falte la combinación: marcar TARIFA_NO_CONFIGURADA y permitir que el administrador la configure.
Para datos de prueba se puede cargar el ejemplo oral de 10 Bs por eje (2 ejes = 20 Bs; 3 ejes = 30 Bs). Indicar en la interfaz que es una tarifa ilustrativa y editable, no una tarifa oficial de Bolivia.
Guardar si el paso corresponde a ENTRADA o SALIDA. La caseta debe poder tener nombre, ubicación, origen y destino. Guardar origen y destino usados al momento del paso, para conservar el historial si la caseta cambia de configuración.
Si la placa existe y el saldo es suficiente: registrar monto, descontar saldo dentro de transacción SQL y marcar PAGADO.
Si la placa existe pero el saldo no alcanza: registrar paso, no descontar saldo, estado SIN_SALDO y generar alerta en tiempo real.
Si la placa fue detectada pero no está registrada: registrar el paso como IDENTIFICADA_NO_REGISTRADA y crear alerta de posible evasión. No descontar saldo.
Si no hay placa legible: guardar la detección como SIN_PLACA o ERROR_OCR; no cobrar; crear alerta de revisión si corresponde.
Si la confianza OCR o ejes no supera el umbral de validación, marcar REVISIÓN_MANUAL; no ejecutar débito automático hasta confirmación del operador.
Si se corrige una detección manualmente, conservar valor original, valor corregido, usuario, fecha y motivo para auditoría.

10. Agente conversacional Qwen
Usar Qwen3.5-Plus mediante la API compatible con OpenAI de Alibaba Cloud Model Studio. El agente debe consultar herramientas del backend: el LLM no ejecuta SQL, no tiene credenciales de PostgreSQL y no inventa estados.
10.1 Flujo del agente
Recibir una pregunta en español y el user_id autenticado.
Identificar intención: consulta de placa, historial, último paso, estado de una placa o aclaración de posible error OCR.
Extraer y normalizar placa; si llega imagen, primero llamar M1+OCR y obtener texto/confianza.
Usar function calling para ejecutar buscar_placa(placa), obtener_historial(placa) o buscar_coincidencias(placa). Las funciones llaman a servicios/repositorios internos que verifican permisos y consultan PostgreSQL.
Entregar al modelo solo el JSON devuelto por las herramientas. Qwen redacta una respuesta breve y humana en español.
Validar que la respuesta no agregue datos ausentes. Si falla Qwen, responder con una plantilla basada directamente en el resultado de la base de datos.
10.2 Cuatro estados exactos
Estado
Condición
Respuesta esperada
REGISTRADA_Y_CON_PASO
Vehículo existe y hay uno o más pasos.
Indicar último paso/historial: fecha, hora, caseta, sentido, categoría, ejes, monto y estado.
REGISTRADA_SIN_PASO
Vehículo existe, pero nunca tiene pasos.
Indicar que está registrada y todavía no se encuentra ningún paso.
IDENTIFICADA_NO_REGISTRADA
Hay una detección/paso con esa placa, pero no existe en vehículos.
Indicar que la cámara la detectó, no está registrada y mostrar evidencia/fecha/caseta disponible.
NO_EXISTE
No aparece ni en vehículos ni en detecciones/pasos.
Indicar que no hay ningún registro coincidente.

10.3 Coincidencias OCR
Comparar placa normalizada con las registradas y detecciones; usar Levenshtein/Damerau-Levenshtein y sustituciones probables O/0, I/1, B/8, S/5, 3/8.
Si una coincidencia supera el umbral, preguntar “No encontré 1238ABC, pero sí 1233ABC. ¿Quisiste decir 1233ABC?”. Mostrar por qué coincide y no reemplazar sin confirmación.
Si existen varias coincidencias posibles, mostrar máximo 3 sugerencias ordenadas por similitud, pero no elegir silenciosamente.
No usar datos de Internet, conocimiento general ni respuestas del modelo para determinar si pasó un vehículo. Solo base de datos/API.

11. Infraestructura, despliegue y seguridad
11.1 VPS y dominio
Contratar Hostinger VPS KVM 2, Ubuntu 24.04 LTS. No comprar/activar un plan sin que el usuario revise el cobro inicial, renovación, plazo y medio de pago.
Registrar un dominio .com propio. Gestionar la zona DNS desde Cloudflare. Crear un registro A para el subdominio peaje que apunte a la IP pública del VPS.
Configurar firewall: permitir SSH de forma restringida y puertos públicos 80/443. PostgreSQL no debe exponerse a Internet.
Instalar Docker Engine y Docker Compose. Desplegar Next.js, FastAPI, PostgreSQL y Caddy en una red privada de Compose.
Caddy recibe el dominio real, enruta /api/* a FastAPI y el resto a Next.js, y genera/renueva HTTPS automáticamente. Comprobar que DNS ya resuelva a la IP y que 80/443 estén abiertos.
No usar subdominio localhost, IP privada, ngrok, túneles hacia laptop ni servidor de desarrollo en la entrega.
11.2 RunPod
Crear un Pod con RTX 3090 de 24 GB como objetivo inicial, usando una imagen CUDA/PyTorch compatible con el entrenamiento de pesos YOLO11 y EasyOCR.
Montar almacenamiento persistente para pesos y entorno. Mantener el endpoint activo en el periodo de revisión. La GPU se factura mientras el Pod esté ejecutándose; detenerlo cuando no haga falta y tener presente que el almacenamiento puede seguir generando costo.
Exponer HTTP port 8000; ejecutar Uvicorn escuchando 0.0.0.0:8000; copiar la URL proxy HTTPS de RunPod a INFERENCE_URL en el VPS.
Configurar la misma INFERENCE_API_KEY en el servicio RunPod y en el VPS. No ponerla en el APK ni en JavaScript del navegador.
Probar desde el VPS la URL /health y luego POST /predict con un frame real. Confirmar respuesta de M1, M2 y M3 antes de conectar la app.

11.4 Seguridad y respaldos
HTTPS obligatorio; cookies web HttpOnly, Secure y SameSite Lax; expiración y revocación de tokens; roles ADMIN/OPERADOR verificados en backend.
